## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン | 選定理由 |
|------|-----------|----------|
| Node.js | v24.19.0 (devcontainer 実測値) | 既存の devcontainer が提供する環境。`node:readline/promises` や `fs.promises` など、本プロダクトが必要とする API がすべて標準で揃っており、追加ランタイムを導入する理由がない |
| TypeScript | ~5.3.0 | エントリが「ID と名前のスナップショットを両方持つ」構造を型で固定する。この二重保持は片方だけを書き忘れると静かに壊れるため、コンパイル時に検出できることの価値が大きい |
| npm | 11.17.0 | Node.js 同梱。`package-lock.json` による依存の厳密固定が可能 |
| ESM | `"type": "module"` | 既存の `package.json` の設定を踏襲する |

> **注記**: `CLAUDE.md` には Node.js v24.11.0 と記載があるが、devcontainer の実測は v24.19.0。
> いずれも v24 系のため本設計に影響はない。`package.json` の `engines` には `">=24.0.0"` を指定する。

### フレームワーク・ライブラリ

**本プロダクトは実行時の外部依存をゼロとする。**

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| `node:readline/promises` | 標準 | REPL の入力ループ、プロンプト表示、対話的な確認入力 | 非機能要件「起動 500ms 以内」に対し、依存パッケージのモジュール解決コストをゼロにできることが最も確実。プロンプト文字列をコマンドごとに差し替える用途にも `rl.question()` で対応できる |
| `node:fs/promises` | 標準 | JSON / JSONL の読み書き、`mode` を指定したファイル生成 | パーミッション 700/600 の要件を `mkdir` / `writeFile` の `mode` オプションで直接満たせる |
| `node:crypto` | 標準 | ID 採番の乱数生成 | `randomBytes` のみを使用。UUID ライブラリを入れるほどの用途ではなく、Crockford Base32 の短縮 ID は自前生成の方が要件に合う |
| `node:os` | 標準 | ホームディレクトリの解決（`~/.timelog`） | — |
| `node:path` | 標準 | パス結合 | — |

**外部依存を採用しなかった選択と理由**:

| 検討した依存 | 一般的な用途 | 不採用の理由 |
|-------------|-------------|-------------|
| Commander / yargs | コマンド解析 | REPL 内の独自文法（`start 3 備考は空白を含む自由テキスト`）を扱う必要があり、CLI 引数パーサの前提と合わない。自前の `CommandRouter` の方が短く済む |
| chalk / picocolors | カラー出力 | 使用する色は 5 種類のみ。ANSI エスケープの薄いラッパで足り、`isTTY` 判定も自前で行う |
| date-fns / dayjs | 日時処理 | 必要なのは「分への切り捨て」「翌日 0 時」「ローカルオフセット付き ISO 8601」の 3 つのみ。いずれも標準 `Date` で完結し、テスト可能な純関数として実装できる |
| lowdb / SQLite | データ永続化 | 単一ユーザー・ローカル完結・月あたり 1,000 件規模。JSONL の追記で十分であり、DB を挟むと「JSONL を `grep` できる」という PRD の可読性要件を失う |
| uuid / ulid | ID 採番 | ID を目視で扱う場面があるため、36 文字の UUID は長すぎる。8 文字の短縮 ID を自前実装する |

**この方針が満たす要件**: PRD セキュリティ要件「ネットワーク通信を一切行わない」は、
コードで通信しないだけでなく**通信し得る依存を持たない**ことによって構造的に保証される。
サプライチェーン経由でテレメトリが混入する経路自体を断つ。

### 既存設定に必要な変更

実装着手前に、以下の 3 点を修正する必要がある。

#### 1. `tsconfig.json` の `moduleResolution` を `NodeNext` へ変更する（必須）

現在の設定は `"moduleResolution": "bundler"` である。この設定は拡張子なしの相対 import
（`import { x } from './foo'`）を許容するが、**tsc は import 文を書き換えずに出力するため、
生成された `dist/*.js` を Node.js の ESM として実行すると `ERR_MODULE_NOT_FOUND` で失敗する。**

Vitest は独自のリゾルバを持つため**テストは通ってしまう**。つまりこの不整合は、
テストが全て緑のまま `node dist/index.js` だけが起動しないという形で顕在化する。
バンドラを導入しない方針である以上、実行環境に合わせる。

```jsonc
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}
```

あわせて、**ソース内の相対 import には `.js` 拡張子を明示する**（`import { x } from './foo.js'`）。
TypeScript の ESM ではソースが `.ts` でも import 先は出力後の `.js` を書く。

#### 2. `@types/node` を実行環境に合わせる

`^20.11.0` が入っているが、ランタイムは v24 系。v20 の型定義では v24 で追加・変更された
API シグネチャを正しく検査できない。`^24.0.0` へ更新する。

#### 3. `package.json` に実行エントリを追加する

```jsonc
{
  "name": "timelog",
  "bin": { "timelog": "./dist/index.js" },
  "engines": { "node": ">=24.0.0" },
  "files": ["dist"]
}
```

`src/index.ts` の先頭に `#!/usr/bin/env node` を置き、ビルド後に実行権限を付与する
（`chmod +x dist/index.js` を `build` スクリプトの後段に追加）。

## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌──────────────────────────────────────────────┐
│  REPL レイヤー                                │ ← 入力ループ・プロンプト・表示整形
│  ReplSession / PromptRenderer /              │
│  CommandRouter / CommandHandlers /           │
│  OutputFormatter                             │
├──────────────────────────────────────────────┤
│  サービスレイヤー                              │ ← ビジネスロジック
│  ProjectService / TimerService /              │
│  ReportService / ExportService / NameResolver │
├──────────────────────────────────────────────┤
│  データレイヤー                                │ ← 永続化
│  ProjectStore / EntryStore / CurrentStore /   │
│  atomicWrite                                  │
└──────────────────────────────────────────────┘
                     ↓
              ~/.timelog/
```

#### REPL レイヤー

- **責務**: 入力の受付とパース、コマンドのルーティング、結果の表示整形、終了・復帰フローの制御
- **許可される操作**: サービスレイヤーの呼び出し、`ReplIo` を介した入出力
- **禁止される操作**: データレイヤーへの直接アクセス、`~/.timelog` のパスを知ること

#### サービスレイヤー

- **責務**: ビジネスロジック（日跨ぎ分割、タスク解決、ID 採番、集計、名前解決）の実装
- **許可される操作**: データレイヤーの呼び出し、他サービスの呼び出し
- **禁止される操作**:
  - `console.*` の直接呼び出し、`readline` への依存
  - 例外による制御フロー（`Result<T, E>` を返す。詳細は後述）
  - **`new Date()` の直接呼び出し**（現在時刻は引数で受け取る）

#### データレイヤー

- **責務**: ファイルの読み書き、パーミッション付与、破損行のスキップ、原子的な置換
- **許可される操作**: ファイルシステムへのアクセス
- **禁止される操作**: 業務ルールの実装（日跨ぎ分割・集計・並び替えを行わない）

### レイヤーを跨がない 3 つの規約

本プロダクトの性質から、通常のレイヤー分離に加えて以下を規約とする。

#### 規約1: 現在時刻はサービスレイヤーに入れない

`TimerService.start(projectId, taskId, note, now: Date)` のように、**現在時刻は必ず引数で渡す**。

理由は日跨ぎ分割にある。この機能の正しさは「金曜夜から月曜朝までの計測が 3 分割される」
といった時刻依存のシナリオでしか検証できない。サービス内部で `new Date()` を呼ぶと、
テストがシステムクロックのモックに依存し、並列実行時に不安定になる。
現在時刻の取得は REPL レイヤーの責務とする。

#### 規約2: サービスレイヤーは例外を投げず `Result` を返す

```typescript
type Result<T, E = AppError> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

想定内のエラー（タスクが見つからない、計測していない、時刻が不正）は、
制御フローの一部であって異常ではない。これらを例外にすると、
「エラーメッセージは何が問題かと次に何をすべきかの両方を含む」という要件を満たすために
`catch` で型を判別し直すことになり、網羅性をコンパイラが保証できない。

`Result` の判別可能ユニオンにすることで、REPL レイヤーの `switch` に漏れがあれば型検査で落ちる。

**例外を使うのは真の異常時のみ**: ファイルシステムの I/O エラー、`projects.json` の破損。
これらは `ReplSession` の最上位で捕捉し、ループを継続させる。

#### 規約3: 表示名の解決は `NameResolver` の 1 箇所に集約する

`show` と `export` が同じタスクに別の名前を表示することは、集計ツールとして許容できない。
ID からの名前解決とスナップショットへのフォールバックを 1 コンポーネントに閉じ込め、
両者がそれを共有することで、実装の重複ではなく構造によって一貫性を保証する。

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 書き込み方式 | 理由 |
|-----------|----------|-------------|-------------|------|
| プロジェクト / タスクのマスタ | `~/.timelog/projects.json` | JSON（整形あり） | 全置換（atomicWrite） | 件数が少なく全体を保持してよい。人が直接編集して修復できるよう整形して書く |
| 実績エントリ | `~/.timelog/entries/YYYY-MM.jsonl` | JSONL（1 行 1 レコード） | **追記**（`appendFile`） | 追記は既存行に触れないため、書き込み中断でも過去の記録を壊さない。月別分割で読み込み対象を一定に保つ |
| 実績エントリの修正（P1） | 同上 | 同上 | 全置換（atomicWrite） | `edit` のみ既存行を書き換える。一時ファイル + `rename` で原子性を確保 |
| 計測中の状態 | `~/.timelog/current.json` | JSON | 全置換（atomicWrite） | `start` 時点で即書き込み。異常終了しても開始時刻を失わない |
| 復帰処理の発動記録 | `~/.timelog/recovery.jsonl` | JSONL（1 行 1 レコード） | **追記**（`appendFile`） | PRD の KPI「復帰導線の発火率」の測定用。タイムスタンプのみを持ち、作業内容は含まない |

### 書き込みの原子性

```typescript
async function atomicWrite(target: string, content: string, mode: number): Promise<void> {
  const tmp = `${target}.tmp.${process.pid}`;
  await fs.writeFile(tmp, content, { mode, encoding: 'utf8' });
  await fs.rename(tmp, target);   // 同一ファイルシステム内の rename は原子的
}
```

- 一時ファイルは対象と**同じディレクトリ**に作る。`/tmp` を経由すると別ファイルシステムになり得て、`rename` の原子性が失われる
- `mode` は `writeFile` の時点で指定する。作成後に `chmod` する実装では、その隙間に他ユーザーが読める瞬間が生まれる

### メモリ常駐とキャッシュ

| データ | 常駐 | 無効化のタイミング |
|--------|------|-------------------|
| `projects.json` の内容 | する | 自身の書き込み時に更新 |
| `listTasks` の整列結果 | する | マスタ変更時 |
| エントリ | **しない** | 都度読み込み |

マスタを常駐させるのは、`resolveTask` が `start` のたびに呼ばれるためである。
エントリを常駐させないのは、`show` / `export` の呼び出し頻度が低く、
常駐によるメモリ増加とキャッシュ不整合のリスクに見合わないため。

**単一プロセス前提**。複数の timelog を同時起動した場合、マスタのキャッシュが古くなり得る。
PRD の「完全に自分専用」という前提から、ファイルロックは実装しない。
ただし `current.json` については、後述の多重起動検知で実害を防ぐ。

### バックアップ戦略

PRD にはバックアップの明示的な要件がないが、非機能要件「確定済みエントリの損失ゼロ」を
支えるために最小限の仕組みを置く。**定期実行のスケジューラは導入しない**（常駐プロセスを増やさない）。

| 対象 | 方式 | 世代 | 復元方法 |
|------|------|------|----------|
| `projects.json` | 上書き前の内容を `projects.json.bak` として保存 | 1 世代 | `mv projects.json.bak projects.json` |
| `entries/*.jsonl` | **バックアップ不要**（追記専用のため上書きで失われない） | — | — |
| `entries/*.jsonl`（`edit` 実行時のみ・P1） | 書き換え前の月ファイルを `YYYY-MM.jsonl.bak` として保存 | 1 世代 | `mv 2026-08.jsonl.bak 2026-08.jsonl` |
| `current.json` | 不要（存在自体が一時的な状態） | — | — |
| `recovery.jsonl` | **バックアップ不要**（追記専用。失っても KPI の集計値が欠けるだけで、作業実績には影響しない） | — | — |

- **世代を 1 つに絞る理由**: 個人ツールで守るべきは「直前の操作でうっかり壊した」ケースであり、
  それ以上の履歴管理はユーザー側のバックアップ手段（Time Machine、`~/.timelog` を git 管理する等）の領分とする
- 起動時に `.bak` が存在する場合でも自動復元はしない。誤った自動復元は正しいデータを上書きし得るため、
  `help recover` で復元手順を案内するに留める

## パフォーマンス要件

### レスポンスタイム

測定環境: devcontainer（CPU 4 コア相当、メモリ 8GB、SSD）、Node.js v24 系。
測定方法: `performance.now()` によるコマンド確定から次プロンプト表示直前までの実測。

| 操作 | 目標時間 | データ規模 | 主な律速要因 |
|------|---------|-----------|-------------|
| REPL 起動 | 500ms 以内 | プロジェクト 100 / タスク 1,000 | Node.js 起動 + `projects.json` の読み込み |
| `start` / `stop` | 100ms 以内 | 同上 | `current.json` の書き込み、JSONL の 1 行追記 |
| `use` / `note` | 100ms 以内 | 同上 | メモリ操作のみ（`use` は I/O なし） |
| `task list` / `project list` | 100ms 以内 | タスク 200 件 | 整列（キャッシュヒット時は表示整形のみ） |
| `show` | 100ms 以内 | 1 日 50 件 / 月 1,000 件 | 月ファイルの全行パース |
| `export` | 1 秒以内 | 月 1,000 件 | 月ファイルのパース + CSV 生成 |
| プロンプト再描画 | 体感遅延なし | — | 経過時間の再計算のみ（O(1)） |

**律速の見立て**: 最も重いのは `show` / `export` における月ファイルの全行 JSON パースである。
1,000 行 × 約 250 バイト = 約 250KB。`JSON.parse` を 1,000 回呼んでも数 ms 台であり、
目標に対して十分な余裕がある。月別分割を採用している限り、蓄積年数はこの数値に影響しない。

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ (RSS) | 80MB | Node.js のベースライン（約 40MB）+ 常駐するマスタ（タスク 20,000 件でも 5MB 未満）+ 一時的な月データ。REPL として起動しっぱなしにするため、常駐コストが体感に影響しない範囲に収める |
| CPU（アイドル時） | 0% | 入力待ちは `readline` のイベント待機。**ポーリングやタイマーによる定期処理を持たない**。起動しっぱなしの前提上、アイドル時に CPU を使う設計は許容しない |
| ディスク | 1 年あたり 3MB 未満 | エントリ 1 行 約 250 バイト × 月 1,000 件 × 12 ヶ月 ≒ 3MB |

## セキュリティアーキテクチャ

### データ保護

| 項目 | 方針 |
|------|------|
| 暗号化 | **行わない**。単一ユーザーのローカルファイルであり、鍵管理を持ち込むと復旧性が下がる。ディスク全体の暗号化は OS の責務とする |
| アクセス制御 | ディレクトリ `0o700` / ファイル `0o600`。`mkdir` / `writeFile` の `mode` で明示し、`process.umask` に依存しない |
| 機密情報管理 | 認証情報・API キーを持たない。設定ファイルに秘密値を保存しない |
| ネットワーク | 送受信を実装しない。実行時依存ゼロにより、間接的な通信経路も持たない |
| ログ | 作業内容（タスク名・備考）を含むため、標準出力以外へのログ出力を行わない。クラッシュレポートの外部送信も行わない。**例外**: 復帰処理の発動記録（`~/.timelog/recovery.jsonl`）はタイムスタンプのみを持ち作業内容を含まないため、この制限の対象外とする（PRD の KPI「復帰導線の発火率」の測定に必要。設計は `docs/functional-design.md` の `RecoveryLogStore` を参照） |

### 入力検証

| 対象 | 検証内容 | 違反時の扱い |
|------|---------|-------------|
| プロジェクト名 / タスク名 | 1〜100 文字、制御文字（`\x00-\x1F`）を含まない、前後の空白をトリム | エラーとして中断 |
| 名前の一意性 | アーカイブ済みを含めて重複しない | エラーとして中断 |
| 時刻入力（`add` / `edit` / 復帰） | `HH:MM` または `YYYY-MM-DD HH:MM` に厳密一致、実在する日時である | エラーとして再入力を促す |
| 日付入力（`show` / `export`） | `YYYY-MM-DD` / `YYYY-MM` に厳密一致 | エラーとして中断 |
| タスク指定 | 数字なら範囲内、文字列なら一致件数が 1 | 範囲外・0 件・複数件をそれぞれ区別してエラー |
| `export --out` のパス | 親ディレクトリが存在する | エラーとして中断 |

### サニタイゼーション

| 経路 | 対策 |
|------|------|
| CSV 出力 | RFC 4180 に従い `,` `"` CR LF をクォート・エスケープ。加えて **CSV インジェクション対策**として、`=` `+` `-` `@` で始まるセルの先頭に `'` を付与する。備考やタスク名はユーザー自身の入力だが、表計算で開いた際に数式として解釈されると値が壊れる |
| ターミナル出力 | タスク名・備考に含まれる制御文字を登録時点で拒否する。ANSI エスケープがそのまま出力され、表示が崩れる／偽の出力を混ぜられることを防ぐ |
| ファイルパス | データディレクトリのパスはユーザー入力から組み立てない（`os.homedir()` + 固定名のみ） |

### エラー表示のセキュア設計

- エラーメッセージにファイルの絶対パスを含めてよい（ローカル単一ユーザーのため情報漏洩リスクがない）。むしろ復旧手順として必要
- 予期しない例外は**スタックトレースを表示したうえでループを継続**する。個人ツールでは、隠すことより自力で原因を追える情報を出すことの価値が高い

## スケーラビリティ設計

### データ増加への対応

**想定データ量**: 月 1,000 エントリ × 36 ヶ月 = 36,000 エントリ、プロジェクト 100 / タスク 20,000。

| 懸念 | 対策 |
|------|------|
| エントリの増加で `show` が遅くなる | 月別ファイル分割により、読み込み対象は常に 1 ヶ月分。蓄積年数に対して O(1) |
| マスタの増加で `task list` が遅くなる | 整列結果をキャッシュし、マスタ変更時のみ再計算する |
| 完了タスクが一覧に溜まる | アーカイブ機能（P1）で表示・解決の対象から外す。**エントリからの参照は生き続ける**ため、過去の集計は影響を受けない |
| 古い月のファイルが増える | ファイル数は年 12 個。ディレクトリ走査を行う処理がない（月キーから直接パスを組み立てる）ため、件数が増えても影響しない |
| `resume` が最新エントリを探すコスト | 当月ファイルの末尾行のみを読む。当月が空の場合のみ前月へ遡る（最大 2 ファイル） |

**アーカイブ戦略**: 古いエントリを別ディレクトリへ退避する仕組みは**設けない**。
月別分割で性能問題が生じないため、退避はファイルの所在を分かりにくくするだけの複雑さになる。

### 機能拡張性

| 拡張軸 | 現時点の設計 | 拡張方法 |
|--------|-------------|----------|
| コマンドの追加 | `CommandRouter` がコマンド名 → ハンドラのマップを持つ | ハンドラを 1 つ追加してマップに登録する。他コマンドに影響しない |
| タスク指定方法の追加 | `resolveTask` が「数字 → 連番」「文字列 → 部分一致」の 2 分岐 | ID は `t_` 始まりで数字始まりにならないため、先頭に ID 分岐を足すだけで既存分岐と衝突しない |
| エントリ項目の追加 | `Entry` に任意項目を追加しても、JSONL の既存行は不足キーを持つだけ | 読み込み時に既定値を補う。**スキーマバージョンによる一括移行を行わずに済む**のが JSONL を選んだ利点 |
| 出力形式の追加 | `ExportService.toCsv()` が文字列を返し、書き出し先は呼び出し側の責務 | 別形式のフォーマッタを並べる。ファイル書き出し・標準出力の分岐は共有できる |
| 集計粒度の追加（週次 / 月次・P2） | `ReportService.daily()` が日付を受けて集計 | 集計ロジック（`summarize`）を期間指定に一般化する。日次はその特殊ケースになる |
| プラグインシステム | **持たない** | 単一ユーザー・単一用途のため、拡張点を外部に開く必要がない。実行時依存ゼロの方針とも相反する |
| 設定のカスタマイズ | **MVP では持たない** | 将来必要になれば `~/.timelog/config.json` を追加する。データディレクトリの位置（`TIMELOG_HOME` 環境変数）はテスト用途で先行して読む |

**`TIMELOG_HOME` 環境変数**: 統合テストで一時ディレクトリを使うために、
データディレクトリのパスを環境変数で上書きできるようにする。
実運用での使用は想定しないが、テスト容易性のために MVP から実装する。

## テスト戦略

### ユニットテスト

- **フレームワーク**: Vitest 2.x
- **対象**: サービスレイヤーの純粋ロジックと、REPL レイヤーの整形処理
  - `splitByDay` / `buildEntries` / `truncateToMinute` / `formatIsoLocal`
  - `resolveTask` / `byRecency` / `generateId` / `summarize`
  - `escapeCsvField` / `PromptRenderer.render` / `CommandRouter.parse`
- **カバレッジ目標**: 80%（branches / functions / lines / statements）。`vitest.config.ts` に設定済みの閾値をそのまま用いる
- **時刻の扱い**: 現在時刻を引数で受け取る規約により、`vi.setSystemTime` に頼らず決定的にテストする

**重点対象**: 日跨ぎ分割の「分割前後で合計が一致する」性質は、境界ケースを列挙する
テーブル駆動テストで検証する（日跨ぎなし / 1 回 / 3 日 / 月跨ぎ / 年跨ぎ / 0 分 / 秒を含む入力）。

### 統合テスト

- **方法**: `fs.mkdtemp` で作成した一時ディレクトリを `TIMELOG_HOME` に設定し、実ファイルに対して検証する。モックは使わない
- **対象**:
  - `start` → プロセス異常終了の模擬 → 再起動 → 復帰フローでの確定、という一連で記録が失われないこと
  - 日跨ぎ・月跨ぎの `stop` が 2 つの月別ファイルへ正しく振り分けられること
  - `projects.json` を削除した状態の `show` がスナップショット名にフォールバックすること
  - JSONL に不正な行を混ぜた場合、該当行のみスキップされること
  - `atomicWrite` の中断を模擬し、既存ファイルが破損しないこと
  - 生成されたディレクトリ・ファイルのパーミッションが 700 / 600 であること

### E2Eテスト

- **ツール**: Vitest + `ReplIo` の差し替え（スクリプト済みの入出力列）
- **シナリオ**:
  - 初回起動フロー（`project add` → `use` → `task add` → `start` → `stop` → `show`）
  - 1 日の典型ワークフロー（複数タスクの切り替え、`note`、小計の一致）
  - 計測中の `exit` が中止され、`stop` 後に正常終了すること
  - 異常終了からの復帰（正常入力 / 不正な終了時刻 / 入力中断時の保持）
  - エラー種別ごとのメッセージ文言

**実バイナリの起動確認**: `moduleResolution` の設定ミスは Vitest では検出できないため、
CI（またはビルド後の確認手順）に **`npm run build && node dist/index.js` の起動確認**を含める。

## 技術的制約

### 環境要件

| 項目 | 要件 |
|------|------|
| OS | Linux / macOS。**Windows はネイティブ環境では対象外**（WSL 経由での利用は可） |
| Node.js | v24.0.0 以上 |
| 最小メモリ | 128MB（RSS 上限 80MB に対する余裕分） |
| 必要ディスク容量 | インストール 1MB 未満 + データ 年 3MB 未満 |
| 必要な外部依存 | **なし**（実行時の npm 依存ゼロ） |
| 端末 | ANSI エスケープに対応した端末。非 TTY 環境では色を出力しない |

**Windows をネイティブ対象外とする理由**: `chmod` 相当のパーミッション（700/600）が
Windows では機能せず、「他ユーザーから読めない」というセキュリティ要件を満たせない。
PRD の想定利用環境が devcontainer であるため、実害はない。

### パフォーマンス制約

- アイドル時にタイマー・ポーリングを持たない。起動しっぱなしの運用が前提のため、経過時間の表示はコマンド確定時の再計算で行う
- 起動時に全月のエントリを読み込まない。読み込むのは `projects.json` と `current.json` のみ
- 同期 I/O（`fs.*Sync`）を使わない。REPL の入力応答をブロックしないため

### セキュリティ制約

- ネットワーク I/O を実装しない。実行時依存を追加しない（この 2 点を CI で機械的に検査する: `dependencies` が空であることの確認）
- 認証・認可の仕組みを持たない。ファイルシステムのパーミッションが唯一のアクセス制御である
- 作業内容を含むデータを、標準出力とデータディレクトリ以外へ出力しない

### 既知の制約と割り切り

| 制約 | 影響 | 割り切りの理由 |
|------|------|---------------|
| ファイルロックを行わない | 複数の timelog を同時起動すると、マスタのキャッシュが古くなり、後から保存した側の変更で上書きされ得る | PRD の「完全に自分専用」という前提。ただし `start` 時に `current.json` が他プロセスによって更新されている場合は警告する（多重起動の検知） |
| タイムゾーンの変更を追跡しない | 記録後に端末のタイムゾーンを変えると、過去エントリの表示時刻が実態とずれる | 記録時のオフセットを ISO 8601 に含めているため、値としては正しく復元できる。海外移動を伴う運用は想定しない |
| 夏時間の重複時刻 | 夏時間の終了時に同じ時刻が 2 回訪れる地域では、`add` の時刻入力が一意に定まらない | JST 環境での運用が前提。分割ロジックは `setHours` ベースであり、境界そのものは正しく求まる |
| `edit` の同時実行 | 月ファイル全置換中に別プロセスが追記すると、追記分が失われる | 上記のファイルロック非採用と同根。単一プロセス前提で許容する |

## 依存関係管理

### バージョン管理方針

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| **（実行時依存）** | — | **`dependencies` は空を維持する**。追加は設計方針の変更に相当するため、レビューを必須とする |
| typescript | ビルド | `~5.3.0`（パッチのみ自動）。マイナー更新は型検査の挙動が変わり得るため明示的に上げる |
| @types/node | 型定義 | `^24.0.0`（ランタイムのメジャーに追随） |
| vitest / @vitest/coverage-v8 / @vitest/ui | テスト | `^2.0.0`。3 つは**同一マイナーに揃える**（内部 API を共有しており、ずれると起動しない） |
| eslint / typescript-eslint | 静的解析 | `^9.0.0` / `^8.0.0` |
| prettier / eslint-config-prettier | フォーマット | `^3.2.0` / `^9.1.0` |
| husky / lint-staged | Git フック | `^9.0.0` / `^15.2.0` |

**原則**:

- `package-lock.json` をコミットし、環境間で同一のツリーを再現する
- 実行時依存が空であるため、**サプライチェーン上の攻撃面は devDependencies に限られる**。
  ビルド成果物 (`dist/`) には第三者コードが一切含まれない
- 依存の追加を検討する際は、「標準モジュールで代替できないか」「起動時間 500ms への影響はどうか」
  「ネットワークアクセスを行う可能性はないか」の 3 点を判断基準とする

### CI で機械的に検査する項目

| 検査 | コマンド | 目的 |
|------|---------|------|
| 型検査 | `npm run typecheck` | — |
| 静的解析 | `npm run lint` | — |
| テスト + カバレッジ | `npm run test:coverage` | 閾値 80% の維持 |
| ビルドと起動確認 | `npm run build && node dist/index.js --version` | `moduleResolution` の不整合など、Vitest では検出できない実行時エラーの検出 |
| 実行時依存ゼロの検査 | `node -e "process.exit(Object.keys(require('./package.json').dependencies ?? {}).length)"` | 実行時依存が追加されていないことの保証 |
