# プロダクト要求定義書 (Product Requirements Document)

作成日: 2026-08-12
ステータス: ドラフト（承認待ち）
元となる資料: `docs/ideas/time-tracking-cli.md`

## プロダクト概要

### 名称

**timelog** - 作業時間ログ記録 REPL ツール

### プロダクトコンセプト

- **打鍵コストの最小化**: 起動しっぱなしの REPL に常駐させ、作業の切り替え時に `start 3` のような 1 コマンドだけで記録を確定させる。CLI の起動コストを毎回払わない
- **プロンプトが状態を語る**: 現在のプロジェクト・計測中タスク・経過時間をプロンプト自身に表示し、`status` 相当の確認コマンドを不要にする
- **記録から集計までを一気通貫**: 記録したデータをそのまま日次のタスク別小計として表示し、月次は CSV としてエクスポートする。集計のための転記作業をゼロにする

### プロダクトビジョン

作業実績の記録は、それ自体が価値を生む作業ではない。にもかかわらず Excel シートへの入力は集中を途切れさせ、月末の集計は毎回まとまった時間を奪っていく。

timelog は、作業実績の記録を「作業の切り替えついでに 1 コマンド打つだけ」の行為に還元する。計測はリアルタイムで走らせ、押し忘れは事後入力で補い、集計はツールが済ませておく。

ローカルで完結する個人専用ツールとして、同期もサーバもチーム共有も持たない。手元のマシンだけで完結することが、そのまま導入コストの低さと信頼性になる。

### 目的

- 作業実績の記録にかかる打鍵コストを、Excel シートへの入力から 1 コマンドまで削減する
- 日次・月次の集計作業を、ツールによる自動集計に置き換える
- 押し忘れ・異常終了といった現実的な運用の破れを、事後入力と復帰導線で吸収し、記録の欠損を防ぐ
- Excel シートによる作業実績管理を完全に置き換える

## ターゲットユーザー

### プライマリーペルソナ: 本プロダクトの作者（ソフトウェアエンジニア）

**基本属性**

- ソフトウェアエンジニア。複数のプロジェクトを並行して担当し、日中に作業対象を何度も切り替える
- 作業実績の提出義務があり、日付・時刻・プロジェクト・タスク単位での記録が必要

**技術スタック / 作業環境**

- ターミナル常駐。エディタとターミナルを行き来しながら作業する
- Node.js / TypeScript を主軸とした開発環境（devcontainer）
- 実績管理は現在 Excel シート。手入力と手集計

**現在の課題**

- 記録そのものより「記録を残す動作のコスト」が高い。Excel を開き、行を追加し、時刻を打ち込む一連の操作が集中を切る
- 結果として記録が後回しになり、思い出しながらまとめて入力することになる
- 月末の集計が面倒。プロジェクト別・タスク別の合計を出すたびに手作業が発生する

**期待する解決策**

- 作業の切り替え時に 1 コマンドだけ打てば記録が残る状態
- 「今どのタスクを計測中か」を確認するための操作が不要な状態
- 月次の集計が、コマンド 1 回と表計算への貼り付けだけで終わる状態

**1 日の典型的なワークフロー**

1. 始業時に timelog を起動。前日の異常終了があれば復帰導線で計測を閉じる
2. `use myproj` で対象プロジェクトを選び、`start 3` で計測開始
3. 打ち合わせやタスク切り替えのたびに `stop` / `start` を打つ
4. 思い出した補足を `note` で計測中エントリに付ける
5. 終業時に `stop` し、`show` で当日の実績とタスク別小計を確認する
6. 月末に `export 2026-08` を実行し、出力された CSV を提出用の表計算に貼り付ける

## 成功指標(KPI)

本プロダクトは完全に個人専用・ローカル完結のため、KPI は利用者数ではなく
**本人の記録行動と集計コスト**を対象とする。測定はすべてローカルの
`~/.timelog/entries/*.jsonl` と本人の実測によって行い、外部への送信は一切行わない。

### プライマリーKPI

- **Excel シートの置き換え率**: 導入 1 ヶ月後の時点で、月次実績の一次記録を Excel へ直接入力した回数が 0 回
  - 測定方法: 本人の申告（月末の振り返り時に確認）
- **日次記録率**: 稼働日の 95% 以上で、その日のエントリが 1 件以上存在する
  - 測定方法: `entries/YYYY-MM.jsonl` を日付で集計し、稼働日数と突き合わせる（導入 1 ヶ月後から測定）
- **1 エントリの記録に要する時間**: 作業切り替え 1 回あたり 5 秒以内（`stop` + `start <番号>` の打鍵完了まで）
  - 測定方法: 導入 2 週間後に本人が 10 回計測し、中央値で評価

### セカンダリーKPI

- **月次集計時間**: 月末の実績集計にかかる時間が 5 分以内（`export` 実行から表計算への貼り付け完了まで）
  - 測定方法: 導入後最初の月末に実測。従来の Excel 手集計との比較を記録する
- **事後修正率**: 全エントリのうち `add` / `edit` による事後入力・修正の割合が 10% 以下
  - 測定方法: エントリに記録された作成経路（リアルタイム計測 / 事後入力）を月次で集計（導入 2 ヶ月後から測定）
- **復帰導線の発火率**: 起動時の計測中状態の復帰処理が発動する回数が月 1 回以下
  - 測定方法: 復帰処理の発動をログとして記録し、月次で集計

## 機能要件

### コア機能(MVP)

MVP の到達点は **「1 日の作業実績を、リアルタイム計測だけで正しく記録し、その日のうちに見返せる」** 状態とする。
補正系（`add` / `edit`）、整理系（`archive`）、外部連携（`export`）は MVP の次の段階に置く。

#### 1. プロジェクト / タスクのマスタ管理

**ユーザーストーリー**:
複数プロジェクトを並行する開発者として、計測時の打鍵を最小化するために、プロジェクトとタスクを事前登録して番号で呼び出せる機能が欲しい

**受け入れ条件**:

- [ ] `project add <名前>` でプロジェクトを登録でき、`~/.timelog/projects.json` に永続化される
- [ ] プロジェクト・タスクの登録時に**不変の内部ID**を採番する。IDは登録後に変化せず、リネームやアーカイブによっても変わらない
- [ ] IDの形式はプロジェクトが `p_` + 英数字、タスクが `t_` + 英数字とする（例: `p_3x8q1v` / `t_7h2k9m`）。数字始まりにはしない
- [ ] IDは同一マスタ内で一意であり、アーカイブ済みを含む既存のIDと衝突しない
- [ ] `project list` で登録済みプロジェクトの一覧が表示される（アーカイブ済みは非表示）
- [ ] `use <プロジェクト>` で作業対象プロジェクトを切り替えられ、プロンプト表示に反映される
- [ ] `task add <名前>` で現在のプロジェクト配下にタスクを登録できる
- [ ] `task list` で現在のプロジェクトのタスク一覧が、**最近使った順**の連番付きで表示される（アーカイブ済みは非表示）
- [ ] 同一プロジェクト内に同名タスクを登録しようとした場合、エラーメッセージを表示して登録を中止する
- [ ] プロジェクト未選択の状態で `task add` / `task list` を実行した場合、`use` を促すエラーメッセージを表示する
- [ ] 存在しないプロジェクト名を `use` に渡した場合、エラーメッセージと登録済み一覧を表示する

**優先度**: P0(必須)

#### 2. タスクの指定方法（番号 + 名前補完）

**ユーザーストーリー**:
1 日に何度も作業を切り替える開発者として、タスク名を正確に打たずに済ませるために、番号でも部分一致の名前でもタスクを指定できる機能が欲しい

**受け入れ条件**:

- [ ] 引数が数字のみの場合、`task list` で表示された連番として解釈する
- [ ] 引数が文字列の場合、現在のプロジェクトのタスク名に対する**部分一致**として解釈する
- [ ] 部分一致の候補が 1 件の場合、そのタスクを選択する
- [ ] 部分一致の候補が複数件の場合、候補一覧を番号付きで表示し、コマンドを中止する
- [ ] 部分一致の候補が 0 件の場合、エラーメッセージを表示してコマンドを中止する
- [ ] 番号の並び順は**最近使った順**（最後に計測されたタスクが先頭）であり、`task list` の表示順と常に一致する
- [ ] アーカイブ済みタスクは番号・名前のいずれでも選択対象に含まれない
- [ ] コマンド引数で指定する番号は表示上の連番であり、内部IDとは無関係である。内部IDは `t_` 始まりで数字始まりにならないため、連番との解釈が衝突しない

**優先度**: P0(必須)

#### 3. リアルタイム計測(start / stop / resume)

**ユーザーストーリー**:
作業実績を記録したい開発者として、記録の手間を最小化するために、作業の開始と終了をコマンド 1 つで記録できる機能が欲しい

**受け入れ条件**:

- [ ] `start <番号|名前> [備考]` で計測を開始し、開始時刻を秒精度の ISO 8601 で記録する
- [ ] `start` 実行時点で `~/.timelog/current.json` に計測状態を即座に書き出す
- [ ] 計測中に `start` を実行した場合、実行中のエントリを自動的に確定（stop 相当）してから新しい計測を開始する
- [ ] `stop` で計測を終了し、エントリを `~/.timelog/entries/YYYY-MM.jsonl` に 1 行追記し、`current.json` を削除する
- [ ] 計測していない状態で `stop` を実行した場合、エラーメッセージを表示して何も変更しない
- [ ] `resume` で直前に確定したエントリと同じプロジェクト・タスクの計測を、現在時刻を開始時刻として再開する
- [ ] `resume` の対象は直前に確定したエントリのタスクであり、備考は引き継がない
- [ ] 確定した 1 エントリが 1 分未満の場合も、作業時間 0 分のエントリとして記録する（破棄しない）
- [ ] 作業時間は開始時刻と終了時刻から**分単位**で算出し、丸め処理を行わない（秒は切り捨て）

**優先度**: P0(必須)

#### 4. 状態表示プロンプト

**ユーザーストーリー**:
計測中かどうかを気にしたくない開発者として、確認操作を不要にするために、現在の状態が常にプロンプトに表示される機能が欲しい

**受け入れ条件**:

- [ ] プロンプトに現在のプロジェクト名、計測中タスク名、経過時間が表示される
- [ ] 表示形式は `[myproj] ▶ 認証API実装 00:23 > ` とし、経過時間は `HH:MM` 形式
- [ ] 計測していない場合は `[myproj] > ` のようにプロジェクト名のみを表示する
- [ ] プロジェクト未選択の場合は `[未選択] > ` を表示する
- [ ] 経過時間はコマンド実行のたびに再描画され、実際の経過時間との誤差が 1 分以内である
- [ ] 経過時間が 100 時間を超える場合も表示が崩れない（`100:00` のように桁を伸ばす）

**優先度**: P0(必須)

#### 5. 備考の記録(note)

**ユーザーストーリー**:
作業の中身を後から思い出したい開発者として、実績に文脈を残すために、計測中のエントリに備考を付けられる機能が欲しい

**受け入れ条件**:

- [ ] `note <テキスト>` で計測中エントリに備考を設定し、`current.json` に反映する
- [ ] `note` を複数回実行した場合、**上書き**する（追記しない）
- [ ] 計測していない状態で `note` を実行した場合、エラーメッセージを表示して何も変更しない
- [ ] 備考が設定されなかったエントリは、備考フィールドを持たない状態で記録される
- [ ] `start <番号|名前> [備考]` の第 2 引数以降も同じ備考として扱われる

**優先度**: P0(必須)

#### 6. データ永続化と日跨ぎ分割

**ユーザーストーリー**:
記録を確実に残したい開発者として、集計を日付単位で成立させるために、エントリが日付境界で自動的に分割されて保存される機能が欲しい

**受け入れ条件**:

- [ ] エントリは `~/.timelog/entries/YYYY-MM.jsonl` に 1 行 1 レコードの JSONL として追記される
- [ ] エントリは日付・開始時刻・終了時刻・作業時間（分）・プロジェクト・タスク・備考（任意）を保持する
- [ ] プロジェクトとタスクは、**内部ID（`projectId` / `taskId`）と、記録時点の名前のスナップショット（`projectName` / `taskName`）の両方**を保持する
- [ ] 開始時刻・終了時刻は ISO 8601（ローカルタイムゾーンのオフセット付き）で保持する
- [ ] `stop` 時に、開始時刻と終了時刻が異なる日付にまたがる場合、日付境界（00:00）ごとに複数のエントリへ分割して記録する
- [ ] 分割は境界の数だけループで行い、分割回数の上限を設けない（3 日以上にまたがる場合も正しく分割される）
- [ ] 分割によって生成された各エントリの作業時間の合計が、分割前の総作業時間と一致する
- [ ] 分割されたエントリが複数の月にまたがる場合、それぞれ該当する月のファイルへ書き込まれる
- [ ] 既存の行を書き換えることなく追記のみで完結する（MVP 時点）
- [ ] 表示・出力時のプロジェクト名 / タスク名は、**IDから `projects.json` を引いて解決した現在の名前**を用いる
- [ ] IDに対応するマスタが見つからない場合（`projects.json` の欠損・破損時）、スナップショットの名前にフォールバックして表示し、警告を表示する
- [ ] `~/.timelog/` および配下のディレクトリは、存在しない場合に自動生成される

**優先度**: P0(必須)

#### 7. 日次実績の表示(show)

**ユーザーストーリー**:
集計の手間をなくしたい開発者として、その日の実績を確認するために、1 日の作業ログとタスク別小計を表示する機能が欲しい

**受け入れ条件**:

- [ ] `show` で当日の実績を表示する
- [ ] `show <YYYY-MM-DD>` で指定日の実績を表示する
- [ ] 表示は「日付 / 開始時刻 / 終了時刻 / 作業時間 / プロジェクト / タスク / 備考」の列を持つ表形式とする
- [ ] 各行の先頭に、その日の中で 1 から始まる**行番号**を表示する（後続の `edit` の指定に用いる）
- [ ] 行は開始時刻の昇順で表示される
- [ ] 表の下に**タスク別小計**（プロジェクト・タスクごとの合計作業時間）を表示する
- [ ] 表の最後にその日の合計作業時間を表示する
- [ ] 作業時間は `H:MM` 形式（例: `1:23`）と分（例: `83分`）の双方が判別できる形式で表示する
- [ ] 該当日のエントリが 0 件の場合、その旨のメッセージを表示する（エラーとしない）
- [ ] 計測中のエントリは表示対象に含めない（確定済みエントリのみ）

**優先度**: P0(必須)

#### 8. 終了フローと異常終了からの復帰

**ユーザーストーリー**:
記録を壊したくない開発者として、押し忘れやクラッシュから記録を守るために、終了時の警告と起動時の復帰導線が欲しい

**受け入れ条件**:

- [ ] 計測中に `exit`（および Ctrl-D）を実行した場合、警告を表示して**終了を中止**し、`stop` を促す
- [ ] 計測していない場合、`exit` は正常に REPL を終了する
- [ ] 起動時に `current.json` が存在する場合、計測中だったタスクと開始時刻を表示し、**終了時刻を対話的に尋ねる**
- [ ] 入力された終了時刻でエントリを確定し、日跨ぎ分割を適用したうえで記録する
- [ ] 終了時刻に開始時刻より前の時刻が入力された場合、エラーメッセージを表示して再入力を求める
- [ ] 復帰処理で入力を中断した場合、`current.json` を保持したまま REPL を起動する（記録を失わない）
- [ ] `current.json` が破損している場合、内容を表示したうえで破棄するかを確認する

**優先度**: P0(必須)

#### 9. ヘルプ

**ユーザーストーリー**:
たまにしか使わないコマンドがある開発者として、マニュアルを探さずに済むように、REPL 内でコマンド一覧を確認できる機能が欲しい

**受け入れ条件**:

- [ ] `help` で全コマンドの一覧と 1 行説明が表示される
- [ ] `help <コマンド名>` で該当コマンドの引数と使用例が表示される
- [ ] 未知のコマンドを入力した場合、エラーメッセージと `help` の案内を表示する

**優先度**: P0(必須)

### 初期リリース後に追加する機能

#### 10. 事後入力(add)

**ユーザーストーリー**:
タイマーを押し忘れることがある開発者として、記録の欠損を埋めるために、後から時刻を指定してエントリを追加できる機能が欲しい

**受け入れ条件**:

- [ ] `add <開始> <終了> <番号|名前> [備考]` で当日のエントリを追加できる
- [ ] `add <YYYY-MM-DD> <開始> <終了> <番号|名前> [備考]` で日付を指定して追加できる
- [ ] 時刻は `HH:MM` 形式で受け付ける
- [ ] 終了時刻が開始時刻より前の場合、エラーメッセージを表示して追加しない
- [ ] 追加されたエントリにも日跨ぎ分割が適用される
- [ ] 既存エントリと時間帯が重複する場合、警告を表示したうえで追加する（重複自体は禁止しない）

**優先度**: P1(重要)

#### 11. 事後修正(edit)

**ユーザーストーリー**:
記録を実態に合わせたい開発者として、間違いを直すために、記録済みエントリの時刻・タスク・備考を修正できる機能が欲しい

**受け入れ条件**:

- [ ] `edit <行番号> <フィールド> <値>` で、**直前に `show` で表示した日付**のエントリを修正する
- [ ] `show` を一度も実行していない場合は、当日を対象とする
- [ ] 修正可能なフィールドは開始時刻・終了時刻・タスク・備考とする
- [ ] `edit <YYYY-MM-DD> <行番号> <フィールド> <値>` で日付を明示して指定できる
- [ ] 修正実行前に、対象となるエントリの現在の内容を表示して確認を求める
- [ ] 存在しない行番号を指定した場合、エラーメッセージを表示して何も変更しない
- [ ] 時刻の修正によって日付をまたぐことになった場合、日跨ぎ分割を再適用する
- [ ] 修正は JSONL ファイルの該当行の書き換えとして実行し、書き換え中の異常終了でファイルが壊れないよう、一時ファイルへの書き出し後にアトミックに置換する

**優先度**: P1(重要)

#### 12. アーカイブ(project archive / task archive)

**ユーザーストーリー**:
プロジェクトとタスクが増え続ける開発者として、番号選択の摩擦を抑えるために、完了したものを一覧から隠せる機能が欲しい

**受け入れ条件**:

- [ ] `task archive <番号|名前>` でタスクをアーカイブできる
- [ ] `project archive <名前>` でプロジェクトをアーカイブできる
- [ ] アーカイブ済みのプロジェクト・タスクは `project list` / `task list` に表示されず、番号・名前の解決対象にもならない
- [ ] `project list --all` / `task list --all` でアーカイブ済みを含めて表示できる
- [ ] アーカイブしても、記録済みエントリは影響を受けず `show` / `export` に表示され続ける
- [ ] 計測中のタスクをアーカイブしようとした場合、エラーメッセージを表示して中止する

**優先度**: P1(重要)

#### 13. CSV エクスポート(export)

**ユーザーストーリー**:
実績を提出する必要がある開発者として、集計作業をなくすために、月次の実績を表計算に貼れる CSV として出力する機能が欲しい

**受け入れ条件**:

- [ ] `export <YYYY-MM>` で該当月の全エントリを CSV として出力する
- [ ] 出力先の既定はカレントディレクトリの `timelog-YYYY-MM.csv` とする
- [ ] `--out <パス>` で出力先を指定できる
- [ ] `--stdout` で標準出力に書き出せる
- [ ] 出力済みのファイルが既に存在する場合、上書き確認を求める
- [ ] 列は「日付 / 開始時刻 / 終了時刻 / 作業時間 / プロジェクト / タスク / 備考」の固定 7 列とし、備考がない行は**空欄**とする(列数は行によって変わらない)
- [ ] **内部IDは列として出力しない**。プロジェクト名とタスク名のみを出力する（同一プロジェクト内の同名タスクは登録できないため、プロジェクト名 + タスク名で一意に定まる）
- [ ] プロジェクト名 / タスク名は、エントリのIDから解決した**現在の名前**を出力する（リネーム後は過去分も新しい名前で出力される）
- [ ] 文字コードは既定を UTF-8 とし、`--bom` オプションで BOM 付き UTF-8 を選択できる
- [ ] 値に `,` `"` 改行が含まれる場合、RFC 4180 に従ってクォートとエスケープを行う
- [ ] 行は日付・開始時刻の昇順で出力される
- [ ] 該当月のエントリが 0 件の場合、ヘッダ行のみのファイルを出力する

**優先度**: P1(重要)

### CLIインターフェース

timelog は単発のサブコマンド CLI ではなく、**起動しっぱなしにする REPL** として動作する。

```bash

```


### 出力データ構成

`show` および `export` が表示・出力する 1 行は、以下の構成を持つ。

| 日付 | 開始時刻 | 終了時刻 | 作業時間 | プロジェクト | タスク | 備考 |
| ---- | -------- | -------- | -------- | ------------ | ------ | ---- |

備考は設定された場合のみ保持する（CSV 出力時は列を固定し、値を空欄とする）。
プロジェクト・タスクは**名前で出力し、内部IDは出力しない**。

### 保存されるデータ構造

エントリは、参照の正としての**内部ID**と、記録時点の**名前のスナップショット**を併せ持つ。

```jsonc
// entries/2026-08.jsonl の 1 行
{
  "date": "2026-08-12",
  "start": "2026-08-12T09:12:00+09:00",
  "end": "2026-08-12T10:17:00+09:00",
  "minutes": 65,
  "projectId": "p_3x8q1v",
  "projectName": "myproj",
  "taskId": "t_7h2k9m",
  "taskName": "認証API実装",
  "note": "リフレッシュトークンの設計も含む"
}
```

この二重保持には次の役割分担がある。

- **ID（正）**: マスタとの対応付けはIDで行う。表示・出力時はIDから現在の名前を解決するため、タスク名を修正すれば過去の実績にも遡って反映される
- **名前（スナップショット）**: `projects.json` を失った場合でも履歴が読める状態を保つための冗長データ。JSONL を単体で `grep` できる性質を維持する目的も兼ねる

### データ保存先

```
~/.timelog/
  projects.json          プロジェクト / タスクのマスタ(内部ID・アーカイブ状態を含む)
  current.json           計測中の状態(start 時に即書き込み)
  entries/
    2026-08.jsonl        月別・1行1エントリ
```

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス

- REPL 起動時間: 500ms 以内（`projects.json` に 100 プロジェクト / 1,000 タスク登録時）
- コマンド応答時間: 100ms 以内（`start` / `stop` / `note` / `use` / 各 `list`）
- `show` の表示: 100ms 以内（1 日 50 エントリ、月次ファイル 1,000 エントリ時）
- `export` の実行: 1 秒以内（1 ヶ月 1,000 エントリ時）
- プロンプトの再描画による体感の遅延がない（コマンド確定から次のプロンプト表示まで 100ms 以内）

### ユーザビリティ

- 初回起動から最初のエントリ記録までを 3 分以内に完了できる（`project add` → `task add` → `start` → `stop`）
- 日常的に使う計測操作（`start` / `stop`）が、タスク名を打たずに 8 打鍵以内で完了する
- `help` のみで全コマンドの仕様を確認でき、外部ドキュメントを参照する必要がない
- すべてのエラーメッセージが「何が問題か」と「次に何をすべきか」の両方を含む
- 破壊的操作（`edit` による書き換え、`export` の上書き）は実行前に確認を求める

### 信頼性

- **確定済みエントリの損失ゼロ**: `stop` で追記されたエントリは、以降の操作によって失われない
- **計測中状態の損失ゼロ**: `start` の時点で `current.json` を書き出すため、REPL の異常終了後も開始時刻を失わない
- 書き換えを伴う操作（`edit`）は一時ファイルへの書き出し後にアトミックに置換し、処理中の異常終了でファイルが破損しない
- JSONL の 1 行が破損していても、他の行の読み取りに影響しない（破損行はスキップし警告を表示する）
- `projects.json` / `current.json` が破損している場合、内容を提示したうえで復旧方法を案内する
- **内部IDは一度採番したら変更されない**。リネーム・アーカイブ・マスタの再編集によってエントリとの対応が切れない
- `projects.json` を失ってもエントリの履歴は判読可能である（名前のスナップショットへフォールバックし、`show` / `export` が継続して動作する）
- 日跨ぎ分割の前後で作業時間の合計が一致する（丸め誤差を含めて 0 分）

### セキュリティ

- **ネットワーク通信を一切行わない**: 外部への送信・受信・テレメトリ収集をすべて行わない
- データはすべて `~/.timelog/` 配下のローカルファイルにのみ保存する
- `~/.timelog/` のパーミッションは `700`、配下のファイルは `600` とし、他ユーザーから読めない状態にする
- 認証・アカウント・鍵管理の仕組みを持たない（単一ユーザーのローカル利用のみを前提とする）

### スケーラビリティ

- 1 ヶ月あたり 1,000 エントリまで、パフォーマンス要件を満たしたまま動作する
- 3 年分（36 ヶ月）のデータを蓄積しても、月別ファイル分割により `show` / `export` の性能が劣化しない
- プロジェクト 100 件 / プロジェクトあたりタスク 200 件まで、一覧表示と番号解決が 100ms 以内で動作する

## スコープ外

明示的にスコープ外とする項目:

- **複数端末間の同期・サーバ連携・クラウド保存**: 完全にローカル完結とする
- **チーム共有・複数ユーザー対応・権限管理**: 個人専用ツールとする
- **GUI / Web UI / エディタ拡張**: REPL のみを提供する
- **時間の丸め処理**: 0.5h 単位などへの丸めや工数表向けの配分は行わない（分単位で保持する）
- **lap（中断）コマンド**: 中断は `stop` → `resume` と同義であり、出力も自然に 2 行に分かれるため導入しない
- **単価・請求金額の計算、および請求書の生成**
- **タグ・ラベルによる横断分類**: プロジェクト / タスクの 2 階層のみとする
- **外部サービス連携**: カレンダー、課題管理システム（Jira / GitHub Issues など）との同期は行わない
- **通知・アラート（OS 通知等）**: MVP 時点ではプロンプト表示以外の通知手段を持たない
- **CSV 以外のエクスポート形式**: Excel 形式（.xlsx）や JSON 出力は行わない
- **過去エントリの削除コマンド**: 誤記録の是正は `edit` による修正で対応する

## 補足: 元アイデアからの決定事項

`docs/ideas/time-tracking-cli.md` の壁打ちで確定した論点は本 PRD にすべて反映済み。
壁打ち時点で「PRD 作成時に詰める」とされていた 2 点について、本 PRD で以下のとおり決定した。

| 論点 | 決定 | 理由 |
| ---- | ---- | ---- |
| `edit` の対象指定方法 | 直前に `show` で表示した日付の行番号を対象とする。日付を明示する場合は `edit <YYYY-MM-DD> <行番号> ...` | `show` で確認してから直すという実際の操作順に沿い、通常は日付の再入力が不要になる |
| `export` の出力先 | 既定はカレントディレクトリの `timelog-YYYY-MM.csv`。`--out` で変更、`--stdout` で標準出力 | 表計算に貼る用途ではファイルが扱いやすく、他ツールに渡す用途では標準出力が扱いやすいため、既定をファイルとしつつ両対応する |

さらに、PRD レビューで挙がった「タスクの内部ID」について以下を決定した。

| 論点 | 決定 | 理由 |
| ---- | ---- | ---- |
| 内部IDの導入 | **導入する**。プロジェクト・タスクに不変IDを採番し、エントリはIDで参照する | 運用開始後に導入すると全 JSONL の移行が必要になる。リネームへの耐性と、アーカイブ済みタスクを過去エントリから引く経路の確保にも必要 |
| エントリの保持内容 | **IDと名前のスナップショットを両方持つ** | IDのみだと `projects.json` を失った時点で全履歴が孤児になり、JSONL を単体で読めなくなる。ローカル完結・プレーンテキストという性質に対して割に合わない |
| 名前の解決方法 | 表示・出力時に**IDから現在の名前を解決**し、引けない場合のみスナップショットへフォールバック | 個人ツールでは打ち間違いの修正が過去にも遡って効くことが期待動作。スナップショットは可読性の担保に徹する |
| CSV へのID出力 | **既定では出力しない**。`--with-id`(P2) を逃げ道として用意 | IDを出すと `projects.json` を Excel に取り込んで VLOOKUP する必要が生じ、KPI「月次集計 5 分以内」とコンセプト「集計の転記をゼロにする」に反する。プロジェクト名 + タスク名で一意に定まるため曖昧さも生じない |
| IDの形式 | `p_` / `t_` プレフィックス付きの英数字（数字始まりにしない） | `task list` の連番は最近使った順で毎回変わるため、内部IDが数字だと `start 3` がどちらを指すか混同する。プレフィックスで視覚的にも解釈上も分離する |
